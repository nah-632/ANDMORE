## 1. MISSION & PRODUCT

**AND MORE** is a bilingual (Arabic-first, English-complete) digital platform for **free, volunteer-delivered online educational sessions**. It connects school students (Primary, Intermediate/Preparatory, Secondary) with **verified** qualified volunteers, and measures the volunteers' contribution as documented hours and impact.

Philosophy: *Knowledge becomes giving. Volunteers build the future. Students become tomorrow's leaders.*

It must be a **real, production-grade system** (database, auth, server-side authorization, audit trail) — not a landing page, not a frontend-only prototype, not a generic tutoring marketplace. There are **no payments** in scope: services are free; do not build any monetization or payment processing.

**Core loop:** Learn (need) → Connect (match) → Teach (session) → Grow (feedback) → Give Back (verified hours/impact).

## 3B. TOOLING, ENVIRONMENT & DEPLOYMENT RULES (LESSONS FROM THE FIRST BUILD) [HARD RULES]

The first build of AND MORE failed repeatedly at deploy time and during local verification. This is a rebuild from scratch. The rules below exist to make each of those failures impossible or caught **before** they reach Render. Each rule has an automated guard; a rule without a guard is not done.

**Environment facts you must design for:**
- **Hosting:** Render (web service) + Supabase. Code lives on GitHub.
- **Local environment is constrained:** the owner works from a phone using iSH (Alpine Linux, musl, aarch64 emulation) where large `npm install` runs can **fail silently** and native binaries (for example Rolldown bindings used by Vitest) can be corrupt. **Do not assume a full local `node_modules`.** **GitHub Actions CI on a normal Linux runner is the source of truth** for install, typecheck, lint, tests and `next build`.

**Pitfall → rule → guard:**

Always import through the `@/` alias. No duplicate helpers. Document the map in `docs/architecture.md`. | `check-imports.mjs` (every relative/alias import resolves and every named import exists as an export); ESLint `import/no-unresolved`, `import/no-duplicates` |

**Local light checks (Node only, zero third-party dependencies; commit them in P0 and wire them into `npm run build` and `npm run verify:light`):**
`check-syntax.mjs`, `check-imports.mjs`, `check-next-conventions.mjs`, `check-i18n-parity.mjs`, `check-design-smells.mjs`, `check-install.mjs`. Each exits non-zero with a clear message and file/line. They must run in seconds on a phone-class environment.

**Zero-dependency means zero:** the light checks must run with **no `node_modules` at all** and must not import any third-party package (no `@babel/parser`, `acorn`, `esbuild`, `typescript`, etc.), only Node built-ins. Plain Node cannot fully parse TSX, so **TypeScript/TSX syntax and type correctness are verified by `tsc --noEmit` and `next build` in CI only**; locally, `check-syntax.mjs` is limited to what Node can verify itself (`node --check` for `.mjs`/`.js`, JSON validity, and simple structural checks). `check-install.mjs` is a **warning locally and an error in CI**. `verify:light` must pass on a machine without `node_modules`. Never move `typescript` or other build tools into `dependencies` to work around the local environment. CI and Render must install dev dependencies for the build (for example `npm ci --include=dev`, and do not set `NODE_ENV=production` before the install). Do not keep scripts from other ecosystems (for example `pytest`) in a Next.js project; `check.sh` is a CI script and is not run locally.

**Git and credentials:**
- Prefer an **SSH deploy key** or the GitHub CLI's credential flow. If a token is needed, use a **fine-grained personal access token scoped to the single repository** with an explicit, deliberately chosen expiry (calendar reminder before it expires) and only the permissions required: **Contents: Read and write** and **Metadata: Read** (add Pull requests / Actions only if used). A token missing "Contents: Read and write" produces 403 on push.
- Never embed a token in a remote URL committed or logged; store it via a credential helper or environment variable. Never print tokens in logs, scripts, commits, or chat.
- Before starting work each session, run a harmless self-test (`git ls-remote origin`, then a dry-run push) so expiry or missing scope is discovered immediately, not mid-task.
- If a push is rejected, **diagnose first** (`git status`, `git fetch`, `git log --oneline --graph origin/main..HEAD`) instead of retrying blindly.

**Deployment on Render:**
- Commit `render.yaml`. Use `npm ci` for install, `next build` for build, `next start -H 0.0.0.0 -p $PORT` for start (or the standalone output equivalent). Pin `NODE_VERSION` to the same version as CI and `engines` in `package.json`.
- Separate **build-time** from **runtime** environment variables. The build must never require runtime-only secrets. Validate env with Zod at boot and fail fast with a clear message listing missing keys (never values).
- Choose and document the Render region (closest available to users, consistent with the data-hosting decision in §12/§22). Note cold-start behavior of the chosen plan in `docs/deploy.md`.
- **Walking skeleton first (P0):** before building features, deploy a minimal app (locale routing, a page in each locale, `/api/health`) through the full CI → Render pipeline and confirm it is green. Only then continue. Every later phase deploys incrementally so errors surface early, in small diffs.

**When a build or deploy fails (mandatory procedure):**
1. Read the **first** error in the log, not the last. Reproduce it in CI or with the light checks.
2. Fix the **root cause**; do not apply blind patches or retry loops.
3. **Add a guard** (check script, lint rule, unit test, or CI step) that would have caught it, then record the incident in `docs/lessons.md` (symptom, root cause, fix, guard).
4. Report it in the phase report under "Known gaps and incidents".

## 4. USERS, ROLES & PERMISSIONS

**Roles:** `student`, `parent` (guardian), `volunteer`, `admin` (with sub-roles: `super_admin`, `reviewer`, `moderator`, `analyst`). A person may hold multiple roles only where explicitly allowed (e.g., parent + volunteer); never student + admin.

**Minors model [DECISION default]:**
- Students under 18 **cannot self-register as independent adults**. A **parent/guardian account is mandatory** and is linked to each minor profile. The guardian gives recorded consent (timestamped, versioned consent text) for platform use and for sessions.
- Students aged 15+ may hold their own login **only if** linked to a guardian account that can view their activity, sessions, and feedback.
- Younger students access sessions through a guardian-controlled flow.
- **Volunteer minimum age: 18** (configurable in `platform_settings`).

**Permission matrix:** Generate a complete role × resource × action matrix as `docs/permissions.md` and implement it as RLS policies + server guards. Every cell must have a test. Key invariants:

- Students/parents see **only their own** and their linked children's data.
- Volunteers see only sessions assigned to them and **limited, need-to-know student info** (first name, stage, subject, learning need) — never contact details, address, school, or full name for minors unless explicitly justified in an ADR.
- Volunteer documents: readable **only** by admins with `reviewer`+ role, via short-lived signed URLs, every access audited.
- Public (anonymous) access: only approved, active volunteers' **public profile fields**, subjects, stages, public content, and aggregate impact numbers.
- Admin actions that change state require a reason where specified, and are written to `audit_logs`.

## 5B. HUMAN, HANDCRAFTED DESIGN DIRECTIVE (ANTI-"AI LOOK") [HARD RULES]

**Goal:** the platform must feel designed by a thoughtful person or small studio who cares about education and community — warm, specific, a little imperfect in the right places — and must **not** resemble a template or an AI-generated site. A visitor should feel *people* behind it, not a generator.

**Typography (humanist, with character):**
- **Arabic headings:** a warm, calligraphy-informed face with real stroke contrast, such as **Amiri** or **Noto Naskh Arabic** (bookish, human) — or a characterful Kufi-leaning face such as **Noto Kufi Arabic** / **El Messiri** for short display lines. **Arabic body/UI:** **IBM Plex Sans Arabic** or **Noto Sans Arabic** (calm, highly legible). Choose one heading family and one body family, no more.
- **English headings:** a humanist or old-style serif with personality (e.g., **Fraunces**, **Newsreader**, **Source Serif 4**); **English body/UI:** a humanist sans (e.g., **Source Sans 3**, **IBM Plex Sans**, **Figtree**). Do **not** default to Inter, Manrope, Poppins, Roboto, or system fonts as the visible identity.
- Pair Arabic and Latin so x-height, weight, and color match visually when mixed on one line. **Show the owner a specimen page (real Arabic + English text, all weights, mobile + desktop) and justify the pairing before using it**; swap if the pairing looks mechanical.
- Use a restrained scale with real hierarchy: large expressive headings, generous line-height for Arabic (~1.7–1.9 body), comfortable measure (45–75 characters). Use weight and size contrast instead of effects. No gradient text, no text shadows, no all-caps Arabic/English shouting.

**Color & surface (warm, not "SaaS blue"):**
- Keep **deep navy** as the anchor, but ground it with **warm paper tones** (off-white/cream backgrounds, not cold gray) and **one warm accent** drawn from the region's materials and light (e.g., terracotta, sand, muted saffron, or deep olive) used sparingly for emphasis. If the owner supplies a logo or palette, derive the accent from it. Soft blue stays as a supporting tone. Document tokens and contrast. **[DECISION]** owner may veto the warm accent; if so, keep warm neutrals.
- **Banned looks:** purple/indigo-to-blue gradients, glassmorphism/frosted cards, neon glows, mesh-gradient blobs, floating 3D shapes, "sparkle" icons, animated gradient borders, dark-mode-by-default tech aesthetic.
- Add subtle tactile quality: faint paper grain or fine line texture on large surfaces, hairline rules, thoughtful dividers, real shadows only where elevation is meaningful.

**Layout (editorial, not template):**
- **No** symmetrical "centered headline + two buttons + three identical feature cards with circle icons" structure. **No** uniform grids of identical rounded cards repeated down the page, no stacked "logo wall", no stat-counter band as the default.
- Compose pages like an editorial piece: asymmetric hero, varied section rhythms, full-bleed moments, large pull-quotes, numbered steps with strong typographic treatment, side-by-side narrative blocks, intentional whitespace. Vary spacing and column structure between sections; respect a grid but not monotony.
- Icons: a single consistent set, used sparingly, never as decoration in colored circles on every item. Prefer typography, numerals, and illustration to icons.
- Components should look considered: distinct button style, form fields with character, custom focus rings, tasteful empty-state illustrations (not generic).

**Imagery & identity (handcrafted):**
- **Logo/wordmark:** an original, hand-drawn or calligraphy-informed mark for "AND MORE" (consider an Arabic-lettering gesture for the "وأكثر"/"And More" lockup and an ampersand/plus motif drawn with a human hand), delivered as clean SVG. An owner-supplied official logo, if provided, takes precedence.
- **Illustration:** a limited, cohesive set of **hand-drawn style** line/shape illustrations (imperfect strokes, human proportions, no glossy vector-stock look, no generic "people with giant phones" or "lightbulb and gears"). Commission-quality direction: describe the illustration style guide (stroke weight, palette, subject matter rooted in Gulf/Saudi everyday learning life — a kitchen table, a laptop, a notebook, tea) and produce original SVGs that follow it. Where you cannot produce quality art, say so and leave clearly designed typographic fallbacks instead of weak art.
- **Photography:** no stock photos and no AI-generated people. Use only real photography with documented consent. **Never show identifiable children** in public marketing without verified guardian consent. Until real photos exist, use illustration/typography, not fake faces.
- **Cultural touch (restrained):** a subtle geometric pattern or arabesque-inspired texture used as an accent (headers, dividers, empty states), never as wallpaper, never kitsch.
- **Hero concept (replaces the node-network idea):** an editorial hero built from large bilingual typography and one hand-crafted illustration or real photograph, expressing "a person sharing knowledge with another person" — warm, quiet, confident. The "AND MORE" idea appears typographically (the ampersand/plus as a recurring graphic motif that gains meaning through the page).

**Motion (human, minimal):** a few meaningful transitions (page-load reveal, hover feedback, step progress). No parallax gimmicks, no endless floating animations, no typing effects, no particle backgrounds. Respect `prefers-reduced-motion`.

**Copy voice (human, specific, local):**
- Write like a thoughtful person from the community, in plain words, with concrete details (what happens in a session, what a volunteer actually does, what a parent can expect). First-person plural ("we") where appropriate; speak to the reader directly.
- **Banned AI-ish patterns:** "Unlock your potential", "Empower", "Seamless", "Elevate", "Cutting-edge", "Leverage", "Journey", "In today's fast-paced world", "Not just X — but Y" repeated as a formula, rule-of-three slogans on every section, excessive em-dashes, exclamation spam, emoji in headings, and Arabic calques of those phrases ("أطلق العنان", "نقلة نوعية", "رحلتك نحو" etc.). The brand line "Not only X — more Y" may appear **at most once or twice** in intentional brand moments, not as a template.
- Vary sentence length. Prefer short, warm, concrete sentences. Arabic copy must read as originally written in Arabic (natural Gulf-friendly MSA), reviewed by a native editor mindset, not translated from English.

**Design process requirements (to prevent template output):**
1. Before building, produce a short **design rationale** (≤1 page): mood, 3 references described in words (e.g., independent bookshops, community newspapers, museum education programs — not other EdTech sites), the typographic pairing, the palette, and what you are deliberately avoiding.
2. Build the design system (tokens, type scale, components) **before** page assembly.
3. Run a **"template smell" audit** on every page: list any element that looks generic (identical card grids, centered-hero formula, stock-like imagery, gradient decoration, filler icons) and fix it. Include the audit and the fixes in the phase report.
4. Test the design with real Arabic content in RTL first, then English — not lorem ipsum, not English-first mirrored.

**LOCKED DESIGN DECISIONS (do not improvise; deviations need the owner's written approval):**

*Typography (four families, no more):*
- Arabic headings: **Amiri** (calligraphic Naskh), used only at 24px and above. Arabic body and all UI text: **IBM Plex Sans Arabic**.
- English headings: **Source Serif 4**. English body and all UI text: **Source Sans 3** (same superfamily style as the serif, so the pairing feels deliberate).
- Confirm each family's supported subsets before use (§3B rule 6). Expose them as `--font-heading` and `--font-body` per locale. Arabic: no letter-spacing, body line-height about 1.8, headings about 1.4. Never use Inter, Poppins, Roboto, Manrope, Cairo or system fonts as visible text.

*Color:* named tokens only: `ink` (graphite text), `navy`, `blue`, `gold` (the warm accent from the owner's logo), `teal` (minor), `paper` (warm off-white background), `line` (hairline border). Sample exact values from the owner's logo, never guess. Solid colors only. Alternate `paper` and `navy` full-width bands to create rhythm.

*Shape and depth:* card and input radius **8px at most**; fully round only for avatars and small tags. 1px hairline borders. **Shadows only on floating layers** (menus, dialogs), none on cards. **No gradients, no blur/glass effects, no glow, no decorative animation.**

*Layout:* text-first, start-aligned hero in an asymmetric split (about 7/5), never a centered headline with two buttons. Steps are a vertical numbered sequence with large numerals, not a row of icon cards. At most **one section per page** may use a grid of equal cards, and never three identical cards each with an icon. Use real content blocks, pull quotes, and varied column structures.

*Icons:* one stroke icon set (Lucide), used sparingly, never inside colored circles or squares.

**Automated design guard:** add `check-design-smells.mjs` (Node built-ins only, part of `verify:light` and CI). It fails on: Tailwind classes `bg-gradient-*`, `backdrop-blur*`, `blur-2xl`/`blur-3xl`, `shadow-xl`/`shadow-2xl`, `rounded-2xl`/`rounded-3xl`, `animate-pulse|bounce|ping` used decoratively, `text-transparent bg-clip-text`; emoji inside headings; and the banned copy phrases of §5B in `messages/*.json` and content files (English and Arabic lists kept in one file `design-guard.config.json`). A deliberate exception needs an inline `design-ok: reason` comment. Owner-supplied wording is listed in an allowlist file, not silently ignored.

**Owner review gate:** in P0 build a `/styleguide` page (`noindex`, deployed to Render) showing, in Arabic RTL and English LTR, the type scale with real text, color tokens, buttons, form fields, a card, a step list, and an empty state. **Stop and wait for the owner to approve it on a phone before building any public page.** Record the approval in `docs/decisions/`.

## 6. LANGUAGE, RTL & INTERNATIONALIZATION

- Arabic is the **default locale**; English is complete. Locale-prefixed routes (`/ar/...`, `/en/...`), `hreflang`, and persisted preference.
- `<html lang dir>` set per locale. Use **CSS logical properties** (`margin-inline-start`, `ps-*`, `text-start`) everywhere; no hard-coded left/right. Mirror directional icons (arrows, chevrons); do **not** mirror logos, media controls, or numerals where inappropriate.
- Message catalogs (e.g., `next-intl`) with **ICU pluralization** (Arabic has six plural forms — handle them correctly). No string concatenation for sentences.
- **All** user-facing text is translated: nav, forms, validation, errors, empty states, emails/notifications, dashboards, legal pages, SEO metadata, ARIA labels.
- Database content that is bilingual (subjects, stages, announcements) uses a structured `name_ar` / `name_en` (or JSONB translations) design — never machine-translate user-generated content silently.
- Formatting via `Intl`: dates, numbers, durations. **[DECISION default]** Gregorian dates with optional Hijri display; Western digits (0–9) by default with user preference for Arabic-Indic; week starts Sunday; default timezone `Asia/Riyadh`, with per-user timezone stored and all timestamps stored UTC.
- Arabic copy: natural, professional, Gulf-friendly Modern Standard Arabic; written by an Arabic copywriter mindset, not literal translation. English copy: plain, human, no hype words ("revolutionary", "game-changing", "next-generation" are banned).
- Mixed-direction safety: handle embedded English names/emails/numbers in Arabic text using `<bdi>`/`dir="auto"`.
- CI check: fail the build if any key exists in one locale but not the other.

## 7. VOLUNTEER LIFECYCLE

**Application status (state machine, enforced in DB and server):**
`draft → submitted → under_review → (interview_scheduled) → approved | rejected | needs_more_info`
Post-approval account states: `active | suspended | deactivated`. Re-application rules after rejection are configurable.

**Registration collects:** full name, profile photo (optional until approval), email, phone, education background, qualification, institution, specialization, subjects, stages, teaching experience, skills, preferred teaching methods, languages, availability, short bio, supporting documents (as required per rules), acceptance of the Code of Conduct.

**Evaluation (admin):** application review, qualification verification, subject/specialization assessment (a structured test: admin-managed question bank or external-score entry — define an extensible `assessments` design), short interview record, scored rubric, internal notes (never visible to the volunteer), decision, rejection reason (templated, bilingual), verification timestamp and verifier.

**[DECISION default]** Because volunteers interact with minors, require **Code of Conduct acceptance** before approval. An admin-recorded reference/background-check status is available as an **optional, configurable** step (off by default); the platform only records the outcome.

**Public visibility** requires: `approved` AND `active` AND profile completeness AND Code of Conduct accepted. Suspension immediately removes visibility and cancels/reassigns future sessions with notifications.

**Classification:** by educational stage (Primary / Intermediate-Preparatory / Secondary), subject (admin-managed list), specialization (admin-managed, hierarchical-capable), teaching style (Explanation, Revision, Exam prep, Homework support, Skills development, Concept clarification — admin-extensible). Provide admin UI to manage taxonomies without code changes.

## 8. STUDENT/PARENT EXPERIENCE & MATCHING

**Session request form:** stage, subject, current level, learning need, preferred time slots, format (individual / small group if enabled), notes (length-limited, scanned by moderation rules; instruct users not to share personal contact details).

**Matching engine (deterministic, explainable, testable):**
- Hard filters first: volunteer approved+active, subject, stage, language if specified, availability overlap, volunteer capacity limits (max active students/week).
- Weighted scoring (weights stored in `platform_settings`, versioned): specialization fit, teaching-method fit, availability fit, recent activity/reliability, feedback score (with minimum-sample smoothing to avoid unfair penalties for new volunteers), load balancing.
- **Every recommendation returns human-readable reasons in the user's language** ("Teaches your stage", "Available at your preferred time", "Matches your subject") and never exposes internal numeric scores to end users.
- Fairness: new volunteers get exposure (cold-start boost, configurable). No hidden demographic features. Document the algorithm in `docs/matching.md`.
- Manual override: admin can assign/reassign with a logged reason. Allow student/parent to pick from recommended volunteers or request admin-assisted matching.
- Optional AI assistance (e.g., summarizing a learning need or suggesting subject tags) is allowed only if: off by default, no minors' personal data sent to third parties without explicit guardian consent and a documented data-processing basis, outputs are suggestions never decisions, and a non-AI fallback exists. Never present an unexplained AI decision.

## 9. SESSIONS

**Lifecycle:** `requested → under_review → matched → pending_volunteer_confirmation → confirmed → in_progress → completed → evaluated`, plus `cancelled_by_student | cancelled_by_volunteer | cancelled_by_admin | no_show_student | no_show_volunteer | expired | disputed`. Define allowed transitions in a single transition table used by both DB triggers/functions and application code.

**Each session stores:** unique ID, student, guardian, volunteer, subject, stage, scheduled start/end (UTC), duration (planned vs actual), status, objectives, notes, attendance (join/leave timestamps per participant), provider reference, feedback links, quality flags.

**Scheduling integrity [HARD RULE]:**
- Prevent double-booking with a **Postgres exclusion constraint** (`tstzrange` + `btree_gist`) per volunteer and per student, plus transactional booking functions. Include a concurrency test.
- Timezone-correct availability (recurring weekly windows + exceptions/blackouts).
- Rules (configurable): minimum notice for cancellation, reschedule limits, reminder schedule, no-show handling, auto-expiry of unanswered requests.

**Video provider abstraction:** define a `VideoProvider` interface (`createMeeting`, `cancelMeeting`, `getJoinInfo`, `getAttendance?`, `healthCheck`). **Ship MVP with one honestly-implemented adapter** (e.g., "external meeting link" provided by the volunteer/admin, or one real provider with working credentials). Zoom / Google Meet / Microsoft Teams adapters are architecture-ready stubs hidden from users until implemented and tested. Do not display unimplemented providers as available.

**Child safety in sessions [HARD RULE, kept simple]:**
- Communication stays inside the platform. Show a clear notice not to share phone numbers or personal accounts (a warning only; no automated blocking).
- For minors, the guardian can see the join link and the session record.
- Recording is **off by default**; never record silently.
- A "Report a problem" button is always available and creates an entry in the admin queue.

**Learning workspace:** objectives, shared notes, whiteboard integration point (provider-agnostic embed or adapter; do not fake it), homework (assign/submit simple items with attachments), attachments (secure upload), post-session learning notes, follow-up recommendations. Simple, focused UI.

## 13. SECURITY (PROPORTIONATE BASELINE) [HARD RULES]

Protect what matters, minors' data, volunteer documents, and access control, without over-engineering the MVP. Build exactly this baseline:

- **Auth:** Supabase Auth with email/password, email verification, password recovery, and session management. Admin MFA is recommended and optional.
- **Authorization:** enforced by RLS and on the server for every route and action. The service-role key is used on the server only and never reaches the client.
- **Input safety:** validate every input on the server with Zod; no raw SQL string building; sanitize any rich text; check ownership on resources accessed by ID.
- **Basic abuse control:** simple rate limits on login, forms, uploads and reports; Turnstile or similar on public forms if spam appears.
- **File uploads:** private buckets, allowed types and size limits, signed expiring URLs, strip location data from images.
- **Transport:** HTTPS, secure cookies, and sensible default security headers.
- **Secrets:** env validation at boot, no secrets in the repo, dependency audit in CI.
- **Errors and logs:** no PII in logs; friendly translated error messages, never stack traces.
- **Backups:** use Supabase backups and write a short restore note in the README.

**Later hardening (post-launch; do NOT build in the MVP unless the owner asks):** mandatory admin MFA, nonce-based CSP, malware scanning of uploads, CAPTCHA everywhere, field-level encryption, formal data-retention schedules, incident/breach runbooks, penetration testing, observer mode for sessions, automated contact-pattern detection.

## 14B. WHATSAPP HANDOFF (BOOKING & VOLUNTEER APPLICATION) [HARD RULES]

**Requirement:** After a user submits a **session request (booking)** or a **volunteer application**, the platform redirects/offers a one-tap handoff to WhatsApp with a **ready-made, prefilled message** addressed to the platform's official number.

**Official number:** `00966508342500` → international format `966508342500`. Store it in `platform_settings` (key `whatsapp_number`, editable by `super_admin`, validated as E.164 digits) and expose it via a single helper. **Never hard-code the number in components or message catalogs.**

**Link format:** `https://wa.me/966508342500?text=<encodeURIComponent(message)>` (digits only, no `+`, no leading zeros). Build links server-side or in one shared utility; unit-test the encoding for Arabic text, line breaks (`%0A`), emojis, and RTL/LTR mixed content.

**Flow (order matters):**
1. The request/application is **validated and saved to the database first** and receives a human-readable **reference code** (e.g., `AM-S-2026-000123` for sessions, `AM-V-2026-000045` for volunteers). The database record is the **source of truth**; WhatsApp is only a convenience channel.
2. The success screen shows the reference code, a clear explanation ("Send this message on WhatsApp so our team can follow up"), and a primary button **"Continue on WhatsApp / تابع عبر واتساب"**. Optionally auto-open after a short, cancelable countdown; never trap the user in a redirect.
3. Provide fallbacks: **copy message** button, visible number, and a QR code on desktop. If WhatsApp is unavailable, the user's request is still valid and tracked in the dashboard.
4. Do not mark anything as "confirmed" because the user opened WhatsApp. Status changes only through the admin/session workflow. Tell the user plainly: *"Your request is received. A team member will confirm it."*
5. Log `whatsapp_handoff_clicked` (reference code, type, locale, timestamp — no message body) for analytics and abuse detection.

**Message templates:** stored as versioned, localized templates (`ar` / `en`), selected by the user's current locale, editable by admins, with placeholders. Keep them short, polite, and structured. Defaults (adjust wording, keep the placeholders):

*Session booking — Arabic*
```
السلام عليكم، أرغب في حجز جلسة تعليمية عبر منصة AND MORE.
رقم الطلب: {reference}
المرحلة: {stage}
المادة: {subject}
الوقت المفضل: {preferred_time}
الاسم: {first_name}
أرجو تأكيد الحجز. شكراً لكم.
```
*Session booking — English*
```
Hello, I would like to book an educational session on AND MORE.
Request ID: {reference}
Stage: {stage}
Subject: {subject}
Preferred time: {preferred_time}
Name: {first_name}
Please confirm my booking. Thank you.
```
*Volunteer application — Arabic*
```
السلام عليكم، أرغب في التطوع عبر منصة AND MORE.
رقم الطلب: {reference}
الاسم: {full_name}
التخصص: {specialization}
المواد: {subjects}
المراحل: {stages}
أرجو مراجعة طلبي. شكراً لكم.
```
*Volunteer application — English*
```
Hello, I would like to volunteer with AND MORE.
Application ID: {reference}
Name: {full_name}
Specialization: {specialization}
Subjects: {subjects}
Stages: {stages}
Please review my application. Thank you.
```

**Privacy & safeguarding constraints (override convenience):**
- **Minimum data in the message.** For student bookings include only: reference code, stage, subject, preferred time, and **first name of the guardian or student** — never the student's full name, school, address, national ID, phone, email, or learning-difficulty details. Volunteer messages may include name and professional fields only; **never attach documents or IDs via the prefilled text**, and tell volunteers to upload documents only inside the platform.
- Users must be told, before the handoff, that WhatsApp is a third-party service and their number becomes visible to the team (short localized notice, linked to the Privacy Policy).
- **This channel is for communication with the AND MORE team only.** It must **not** be used to exchange contact details between volunteers and students; the "no off-platform contact" rule in §9 still applies. Keep a short staff note (`docs/whatsapp-protocol.md`) on who monitors the number and on never sharing student data in groups.
- Fix the message at generation time from database values; sanitize and length-limit every interpolated field (WhatsApp URLs have practical length limits; truncate safely and keep the reference code last-resort intact) and strip control characters. Never include free-text notes entered by users.
- Scope: this is a **plain handoff link** (`https://wa.me/966508342500?text=...`) to the official number. **No WhatsApp Business API or Business Platform integration is built or needed.** Do not build or claim automated WhatsApp notifications, delivery tracking, or two-way sync. System notifications use in-app and email only.

**Testing:** unit tests for link/template generation in both locales; E2E test that after booking and after volunteer application the correct localized link (with the saved reference code) is shown; test that no sensitive fields appear in the generated text; test copy/QR fallbacks and that the flow works with WhatsApp unavailable.
